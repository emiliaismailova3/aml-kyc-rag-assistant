# 00. Весь проект на одной странице + сценарий демо на 10 минут

## Что это за система (простыми словами)
Это «умный сотрудник компании» для факторинга/финтеха. Он умеет:
1. **Отвечать на вопросы по документам** (законы, рекомендации FATF) и показывать, откуда взят ответ: файл и страница.
2. **Читать инвойсы** (PDF или фото) и превращать их в таблицу полей, проверяя, что данные не нелепые.
3. **Узнавать компанию**: «XEZER LOGISTIKA LLC» и «Xəzər Logistika MMC» — это одна фирма.
4. **Сам собирать новые документы** из интернета по расписанию, не дублируя уже собранное.
5. **Работать как агент**: сам решает, чем воспользоваться (поиск по документам, SQL по базе, чтение инвойса,
   калькулятор, интернет).
6. **Принимать голосовой вопрос**.
7. **Не падать**: повторяет запросы при сбоях, переключается на запасного провайдера, пишет журнал затрат,
   а если всё сломалось — честно говорит «передайте человеку».

## Карта (кто за что отвечает)
```
        голос --Whisper--> текст ----+
                                     v
 вопрос ---------------------> АГЕНТ (5 инструментов)
                                     |-- search_knowledge_base --> хранилище векторов (Chroma | pgvector)
                                     |-- sql_query (только чтение) --> PostgreSQL: компании, инвойсы
                                     |-- extract_invoice -----------> конвейер инвойсов
                                     |-- calculator / internet_search
 файл инвойса --> текст (слой PDF или OCR) --> LLM --> JSON --> проверка правил --> сопоставление компании --> БД
 расписание (Celery beat) --> скачать --> очистить --> дедупликация --> хранилище векторов
 любой вызов LLM --> обёртка: маленькая/большая модель, повторы, запасной провайдер, журнал -> /stats
```
Подробности по каждому блоку: `01-invoices.md` ... `07-voice.md` в этой папке.

## Что честно сказать на собеседовании
- Сделано и **проверено вживую**: RAG с цитатами; pgvector (2176 фрагментов, HNSW); SQL-инструмент агента на
  PostgreSQL с ролью только для чтения; сборщик с настоящим Redis и воркером Celery; извлечение инвойсов с текстовым слоем
  (5/5 верно); сопоставление компаний (52 пары); журнал и `/stats`.
- **Не проверено:** распознавание текста со сканов (Tesseract не был установлен); запасной переход на Anthropic/OpenAI
  (нет ключей, только тесты с имитацией); точность голоса; всё на синтетических данных.
- Это нормально и лучше, чем преувеличивать: на вопрос «а это работает?» у тебя есть точный ответ по каждому пункту
  (`docs/STATUS.md`).

## Сценарий демо на 10 минут
Подготовка (один раз, до собеседования, ~15 минут): `docker compose --profile full up -d postgres redis`,
`python -m src.vectorstore`, `python -m scripts.seed_demo_db`, ключ Groq в `.env`.

| Минуты | Что запускаешь | Что показываешь и говоришь |
|---|---|---|
| 0-1 | `uvicorn src.api:app` и `streamlit run src/streamlit_app.py` | «Вот интерфейс. Под ним FastAPI, векторная база и агент». Показать карту выше |
| 1-3 | В UI: «What does beneficial ownership mean?» | Ответ с `[1]`, `[2]` и чипами источников «файл · стр.». «Если в документах нет ответа, система отказывается, а не придумывает» (задай вопрос вне темы) |
| 3-5 | В UI (режим агента): «How many invoices in the database are in EUR and what is their total?» | Раскрыть вызов инструмента `sql_query`. «SQL проходит 5 слоёв защиты, агент видит только две витрины, роль только для чтения» |
| 5-6 | «Extract the data from the invoice file inv_01_text.pdf» | Раскрыть `extract_invoice`: поля и найденная компания, метод `voen`. «Проверки: VÖEN 10 цифр, сумма позиций = итог; при ошибке JSON возвращается модели, потом человеку» |
| 6-7 | `python -m src.matching.evaluate` | Таблица по типам искажений. «Precision 1.0 на 52 парах, но данные синтетические; сомнительные уходят человеку» |
| 7-8 | `curl localhost:8000/stats` | p50/p95 задержки, доля ошибок, стоимость. «Короткие запросы идут на малую модель; при сбое повтор с паузой и jitter, потом запасной провайдер» |
| 8-9 | `celery ... worker`, затем `collect_all.delay()` дважды | Первый запуск: `ingested`; второй: `duplicate`. «Идемпотентность по хэшу текста» |
| 9-10 | Вопросы | Честно назвать ограничения из раздела выше |

Голос показывать только если успеешь проверить заранее: `curl -F "file=@q.wav" -F "language=en" localhost:8000/ask_voice`.

## Главные термины в двух словах
- **RAG**: найти нужные куски документов и дать модели только их, чтобы она не выдумывала.
- **Эмбеддинг**: текст в виде набора чисел; близкие по смыслу тексты дают близкие числа.
- **pgvector**: расширение PostgreSQL для поиска по таким числам; **HNSW**: быстрый индекс для этого поиска.
- **Idempotent**: повторный запуск ничего не портит и не дублирует.
- **Backoff + jitter**: ждать всё дольше между повторами, чуть случайно, чтобы клиенты не бились одновременно.
- **p95**: время, быстрее которого отвечают 95% запросов (хвост задержек).
- **Human-in-the-loop**: когда система не уверена, решает человек.
