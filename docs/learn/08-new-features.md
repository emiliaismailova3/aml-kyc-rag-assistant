# Новое в проекте: что добавлено и что говорить на интервью

Это дополнение к шпаргалке. Здесь только то, что появилось последним: стриминг ответа, перевод и резюме, MCP-сервер, замер распознавания речи. Всё лежит в ветке feature/vacancy-gaps (после слияния в main говори просто «в проекте»).

## 0. Зачем это добавили (связь с вакансией Ferrum Capital)

- «Speech-to-text, translation, summarization, real-time AI processing» (обязанности) → STT измерен, перевод и резюме есть, ответ идёт потоком.

- «Logging, monitoring, retry, fallback» → всё новое идёт через тот же LLM-клиент с повторами, запасными провайдерами и логом.

Чего по-прежнему НЕТ (говори прямо): запись с микрофона в реальном времени, перевод речи, подключение Gemini (цепочка провайдеров настраивается, но Gemini не подключён), оценка качества перевода.

## 1. Стриминг ответа (POST /ask_stream)

Простыми словами: как печатает человек в чате. Слова появляются по мере написания, а не после того, как весь ответ готов. Для пользователя система кажется быстрее.

Как устроено:
- Это server-sent events (SSE): сервер держит соединение открытым и шлёт события.
- События: token (кусочек текста), потом один done (итоговый ответ, источники, время до первого куска).
- Повтор и переключение на запасного провайдера работают только до первого куска. Если пользователь уже увидел текст, смена модели дала бы другой ответ. Поэтому при обрыве посреди ответа приходит событие error с флагом escalate_to_human.
- Итоговый текст в done очищается от лишних маркеров цитат, а сырой поток очистить нельзя.

Что проверено: тесты с поддельными провайдерами; одна живая проверка на Groq, первый кусок пришёл через 617 мс (одно измерение, не среднее).
Что НЕ сделано: число токенов в логе оценочное (примерно 4 символа на токен), потому что стрим не отдаёт точные данные; стриминг с микрофона не делала.

Вопрос: «Зачем стриминг?» → Чтобы пользователь видел ответ сразу, а не ждал несколько секунд. Задержка воспринимается меньше, хотя общее время то же.
Вопрос: «Что если провайдер упал посреди ответа?» → Приходит error-событие и запрос уходит человеку. Менять провайдера на лету не стала: ответ получился бы другим.

На азербайджанском:
- Cavab hazır olanda deyil, yazıldıqca hissə-hissə göndərilir. Beləliklə istifadəçi gözləmir.
- Birinci hissə təxminən 0,6 saniyəyə gəldi (bir canlı yoxlama).

## 2. Перевод и резюме (POST /translate, POST /summarize)

Простыми словами: обычный вызов LLM с чёткой инструкцией. Для перевода: «переведи, но имена, числа, даты и реквизиты оставь как есть, ничего не добавляй». Для резюме: «не больше N предложений и только факты из текста».

Как устроено:
- Языки: английский, азербайджанский, русский, турецкий.
- Длинный текст режется на куски (до 6000 символов, по границам абзацев), каждый кусок переводится или сжимается отдельно. Для резюме это map-reduce: сначала резюме кусков, потом резюме резюме. Предел запроса 60 000 символов.
- Всё идёт через общий LLM-клиент: короткие тексты на малую модель, повторы, запасные провайдеры, лог стоимости.
- Глоссарий (data/glossary.json): фиксированный перевод терминов AML/KYC. Живая проверка: «beneficial owners» сначала перевелось как «Mənbə sahibləri» (плохо), с глоссарием стало «Benefisiar mülkiyyətçilər».

Честно про качество:
- Качество перевода и резюме НЕ измерено. Глоссарий писала не носитель языка и не юрист, его нужно проверить у команды.
- В русском тесте получилась неуклюжая фраза про «клиента факторинга счёт-фактура»: модель иногда путает порядок слов.

Вопрос: «Как контролируешь качество перевода?» → Сейчас так: глоссарий терминов, инструкция не менять числа и имена, тесты на логику. Метрики нет. Дальше: выборка с проверкой человеком, потом автоматическая оценка другой моделью.
Вопрос: «Как резюмируешь длинный документ?» → Map-reduce: режу на куски, сжимаю каждый, потом сжимаю сжатое.

На азербайджанском:
- Tərcümənin keyfiyyətini ölçməmişəm. Terminləri lüğətlə (glossary) sabitləşdirmişəm, növbəti addım insan yoxlamasıdır.
- Uzun mətni hissələrə bölürəm, hər hissənin xülasəsini çıxarıram, sonra xülasələrin xülasəsini yazıram.

## 3. MCP-сервер (python -m src.mcp_server)

Простыми словами: MCP это как USB-C для ИИ. Один стандартный разъём, чтобы любое ИИ-приложение (Claude Desktop, IDE, другой агент) могло подключиться к твоим инструментам, не переписывая интеграцию под каждое.

Что выставлено наружу (5 инструментов): поиск по базе знаний AML/KYC, SQL только на чтение (две view), извлечение данных из счёта, перевод, резюме.

Важное:
- Инструменты вызывают ту же самую логику, что и встроенный агент. Поэтому SQL-защита (только SELECT на двух view), защита от выхода за пределы папки со счетами и надёжный LLM-клиент работают и через MCP.
- Транспорт stdio: так запускают настольные клиенты.
- Нужен отдельный пакет (requirements-mcp.txt, версия mcp 2.x; в ней FastMCP переименован в MCPServer).

Что проверено: тесты; настоящий stdio-клиент увидел 5 инструментов и получил отказ на запрос DROP TABLE.
Что НЕ сделано: в самом приложении Claude Desktop не проверяла; авторизацию и разграничение прав не делала.

Вопрос: «MCP или function calling?» → Function calling: модель вызывает функции, описанные внутри одного приложения. MCP: стандартный протокол, инструменты живут в отдельном сервере, и к ним подключается любой клиент. Одно не отменяет другое: клиент может использовать MCP-инструменты через function calling.
Вопрос: «Что с безопасностью MCP?» → Через MCP не открыт произвольный SQL: тот же фильтр, что у агента. Но авторизации нет, сервер локальный. Для продакшена нужны аутентификация и аудит.

На азербайджанском:
- MCP süni intellekt tətbiqlərinin alətlərə qoşulması üçün ümumi standartdır, süni intellekt üçün USB-C kimi.
- Alətlər eyni məntiqi işlədir, ona görə SQL qorunması MCP vasitəsilə də qüvvədədir.

## 4. Замер распознавания речи (WER)

Что такое WER: доля неверных слов. Считают ошибки трёх типов (заменили слово, пропустили, добавили лишнее) и делят на число слов в эталоне. 0 идеально, 1 это ошибка в каждом слове. Чем меньше, тем лучше.

Как мерила: 5 коротких фраз, один голос, модель Whisper base. Скрипт scripts/check_voice.py, фразы в data/voice_eval/phrases.json, результат в data/eval_results/voice_wer.json.

Результат:
- Английский (3 фразы): WER 0,08. Две фразы точные, в одной «ownership» услышано как «overmanship».
- Азербайджанский (2 фразы): WER 0,39. Смысл понятен, но теряются буквы ə, ü, ş, а слово «faktorinq» искажено.

Что нашла:
- Без подсказки языка Whisper принял одну английскую фразу за другой язык и выдал мусор. Поэтому язык нужно передавать явно (API это поддерживает).
- Пробовала модель побольше (small) и подсказку со словами предметной области. Стабильного выигрыша нет, подсказка даже ухудшила. Поэтому оставила base.

История, которую можно рассказать (показывает зрелость):
Сначала я решила, что Whisper перепутал «450» и «550». Проверила и поняла: в записи я сама сказала «550», а ошибся мой эталонный текст. Вывод: сначала проверяй эталон, потом обвиняй модель. Цифры я пересчитала.

Честно про ограничения: выборка крошечная (5 фраз, один голос, без шума и акцентов), это ориентир, а не оценка точности.

Вопрос: «Как проверяла качество STT?» → Считала WER на пяти своих записях: английский 0,08, азербайджанский 0,39. Выборка маленькая, поэтому это ориентир.
Вопрос: «Почему азербайджанский хуже?» → У Whisper мало обучающих данных на азербайджанском, особенно с буквами ə, ü, ş. Улучшила бы большей моделью, облачным API, дообучением или подтверждением текста пользователем.
Вопрос: «Что делать с ошибками в числах в финансах?» → Показывать пользователю распознанный текст до выполнения, а для сумм и реквизитов требовать подтверждения.

На азербайджанском:
- İngilis dilində WER 0,08, Azərbaycan dilində 0,39 oldu.
- Azərbaycan dili üçün Whisper-in təlim məlumatı azdır, ona görə ə, ü, ş kimi hərfləri itirir.
- Qiymətləndirmə kiçik nümunədə aparılıb (5 cümlə), buna görə yalnız istiqamət göstərir.
- Əvvəlcə səhv olduğunu düşündüm, sonra yoxladım: səhv modeldə yox, mənim yazdığım etalon mətndə idi. Dərs: əvvəlcə etalonu yoxla.

## 5. Цифры для памяти

- Тесты: 249 проходят, 5 пропускаются без PostgreSQL и Redis (ruff чистый).
- Голос: английский WER 0,08 (3 фразы), азербайджанский 0,39 (2 фразы), модель base.
- Стриминг: первый кусок через 617 мс (одно живое измерение, Groq).
- MCP: 5 инструментов, транспорт stdio.
- Перевод и резюме: 4 языка, кусок до 6000 символов, предел запроса 60 000.
- Глоссарий: 9 терминов для азербайджанского, 8 для русского.

## 6. Чего НЕ говорить

- «Голос работает идеально» → английский хорошо, азербайджанский слабее.
- «Перевод качественный» → качество не измерено, есть глоссарий.
- «Есть real-time» → стриминг ответа есть, потоковой записи с микрофона нет.
- «MCP готов для продакшена» → работает локально, без авторизации.
- «Подключены все провайдеры» → в цепочке OpenAI, Anthropic, Groq; Gemini не подключён.
